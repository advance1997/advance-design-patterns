# 享元模式：共享催收材料规则，隔离案件归集状态

## 业务场景

诉讼材料归集时，不同案件遵循相同的材料规则：借款合同和还款流水是必需材料，外呼录音是可选材料。规则内容可以共享，但每个案件已经归集了哪些材料必须分别记录。

示例中的 `DEMO-001` 已归集借款合同，`DEMO-002` 已归集还款流水。两个案件的必需材料清单相同，归集进度不同。这里只用内存对象演示，不访问文件、数据库、对象存储或远程服务。

## 享元模式解决什么问题

当许多对象重复保存相同且不可变的数据时，可以把这部分数据提取为共享享元；每个业务对象只保留自己的状态。这里：

| 状态 | 示例 | 所有者 | 是否共享 |
| --- | --- | --- | --- |
| 内在状态 | 材料编码、是否必需 | `MaterialRuleFlyweight` | 相同规则由工厂复用 |
| 外在状态 | 案件编号、案件必需材料清单、已归集材料 | `CollectionTask` | 每个案件独立保存 |

不要把案件编号或已归集列表放入享元，否则一个案件的变化会污染其他案件。享元也不是单例：工厂按规则键缓存多条规则；单例只关心实例数量，并不能代替这层状态划分。

## 版本演进

| 版本 | 做法 | 两个案件的规则对象数 | 结论 |
| --- | --- | ---: | --- |
| v1-naive | 创建每个案件时都重新创建三条规则 | 6 | 规则重复创建，案件归集状态各自保存 |
| v2-refactor | 将规则创建提取到 `buildRules` 方法 | 6 | 代码位置集中，但没有共享对象 |
| v3-pattern | `FlyweightFactory` 按规则键缓存不可变规则 | 3 | 规则共享，`CollectionTask` 继续独立保存案件状态 |

```text
CollectionService
├── FlyweightFactory ── 缓存 MaterialRuleFlyweight（材料编码、是否必需）
└── CollectionTask(DEMO-001 / DEMO-002)
    ├── 案件自己的必需材料清单
    └── 案件自己的已归集材料清单
```

测试会显示两案相同的必需材料、不同的已归集材料，以及 v3 工厂缓存的 3 个规则对象。v1/v2 的对象创建数量仅用于观察本例的重复创建，不是性能基准，也不表示生产环境一定能获得可观收益。

## 适用边界

适合大量对象需要共享相同、不可变数据的场景。规则很少时直接创建更简单；生产缓存还需定义规则版本、租户隔离、更新与并发策略。本例的 `LinkedHashMap` 只适合单线程教学，不是生产缓存配置。

## 测试与运行

每个版本只有一个打印式用例，用同一场景观察“规则是否共享”和“案件状态是否隔离”，没有断言框架、性能压测或并发测试。

```bash
mvn -f patterns/structural/flyweight/pom.xml test
mvn -f patterns/structural/flyweight/v3-pattern/pom.xml test
```

所有版本均使用 Java 8 普通类独立演进；本例不引入 Spring、数据库或远程服务。
